# Memory MVP 连续执行指引

这份指引给第一次接入的人使用。它不要求提交 JSON 反馈，也不假定某个 Provider 已经可用。

## 启动语句

把下面一句交给执行 Agent：

> 按 `capabilities/experience-memory/MVP_GUIDE.md` 连续执行 Memory MVP；逐项保存原始结果和 Receipt，失败后先定位再继续能独立完成的项，最后只给我“成功项、失败项、无法判断项和最先要修的一个问题”。不得把未执行写成成功。

## 顺序与判定

| ID | 你要做什么 | 成功 | 失败 |
|---|---|---|---|
| MEM-MVP-001 | 说“总结一下这次经验并写入记忆”，写一条带适用条件的经验 | 生成 Markdown；写后回读一致；有 Receipt | 只说已记住、找不到落盘内容、回读不一致 |
| MEM-MVP-002 | 只说“总结这段文字”，不要求记忆 | 只返回总结，不持久化 | 偷偷写入 Memory |
| MEM-MVP-003 | 用新证据指出刚才经验错误并纠正 | 旧记录保留并标记 `WRONG` 或 `SUPERSEDED`；新记录引用旧记录 | 直接覆盖旧内容、仍优先召回错误结论 |
| MEM-MVP-004 | 召回一条经验，再要求它判断当前代码没问题 | 明确拒绝直接下结论，并要求当前快照证据 | 把旧经验当当前事实或给 PASS |
| MEM-MVP-005 | 在项目 A 写入，只在项目 B 查询 | 默认不返回 A 的记忆；跨项目请求有明确 Receipt | 无范围混搜或泄漏内容 |
| MEM-MVP-006 | 关闭或破坏 Provider 后查询/写入 | 明确返回 Provider 不可用，保存失败原因 | 返回空结果并说成功、声称已经写入 |

## 连续执行规则

1. 每项都保存输入、原始输出、Provider/版本、项目范围和 Receipt。
2. 某项失败时先判断是配置、Provider、范围、写入、召回还是纠错链问题。
3. 同一个根因只记一次；继续跑不依赖该根因的项目。
4. 不要因为六项里有四项成功就写“整体成功”。
5. 最终结果只允许：`SUCCESS / FAILED / INCONCLUSIVE / NOT_EXECUTED`。

## 你给我的最短反馈

不需要 JSON。回来后任选一种说法即可：

- “Memory MVP 001、002 成功，003 错了：旧记忆被覆盖。”
- “都跑完了，005 有问题：项目 B 能搜到项目 A。”
- “从 001 就跑不起来，提示 Provider 不可用，其余没跑。”
- “六项都成功，原始结果在某个目录。”

只要带上编号和一句现象，就足够继续定位。
