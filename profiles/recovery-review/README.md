# Recovery Review Profile

这是对独立能力的一种可选组合，用于“需求与协作信息可能不完整、AI 已留下修改、需要在 Windows 侧尽可能严谨地恢复事实并持续自主检查”的场景。它不取代 `code-fact`、`build-dependency-audit`、`change-safety` 等能力的独立入口。

## 标志性启动事件

系统先生成可阅读的 Alignment Preview，明确仓库、Revision、未提交改动、多人协作边界、尚未到达的协作者代码、权威依据、权限与执行范围。用户确认无误后必须原样发送：

> 确认并锁定本次审查，开始自主执行

Runner 规范化所有锁定字段并计算 SHA-256。自此进入无人值守阶段：READY 项持续运行，不因普通检查失败或一个局部阻塞反复停下来问用户。真正缺少授权、密钥、外部输入或语义决定时，Runner 先完成诊断、尝试安全替代方案并继续不受影响的工作，最后才把去重后的最小问题列为 `WAITING_HUMAN`。

## 三条核心判定原则

1. **证据优先于语气。** 没有能追溯到固定源码快照、有效检查或用户提供错误的证据，就不能说“没问题”。
2. **外部红覆盖本地绿。** 用户提供的可复现报错是新证据。若本地检查为绿，结论是“证据冲突，必须解释”，不是继续宣布通过。
3. **预检只在证明自己生效后才有意义。** Canary、索引新鲜度、编译器/flags/include/宏/生成文件/target 等价性都进入证据包。Windows 预检可以发现问题，但环境不等价时不能冒充正式构建或 DT。
4. **合入文本必须脱离私聊仍然成立。** 修改后的代码、注释、名称、测试和消息只能引用仓内可获得的业务、设计与工程上下文；会话轮次、用户与 AI 审批语或 `fix1.1` 一类私人标签必须在交付前改写为稳定含义。

## 组合而不耦合

Profile 只持有 Claim/Evidence/Receipt 的公开引用。Code Fact 选择 CodeGraph、clangd、词法扫描或其他 Provider 的过程属于 `code-fact` 能力内部；Profile 不知道也不依赖 Provider 私有数据库。这样，普通搜索可以单独用 Code Fact，Recovery Review 也能在 Provider 替换后保持稳定。

## 最终交付

专业版、小白版和机器版报告从同一个事实集生成。它们可以使用不同表达，但错误数、严重度、证据引用、局限与结论必须完全一致。任何 `INCONCLUSIVE` 都要保留，不能为了“漂亮答卷”改写为 PASS。
