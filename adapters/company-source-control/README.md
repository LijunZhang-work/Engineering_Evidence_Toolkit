# 公司多仓源码控制适配器

状态：**DESIGNED**  
真实项目验证：**NOT_RUN**

这个适配器承接公司 Python 脚本化的拉取、多仓工作区、修订冻结和提交语义。它的目的不是替换公司工具，而是把公司工具的结果转换成稳定、可审计的 `WorkspaceSnapshot`，并阻止通用能力在不知道副作用的情况下直接调用脚本。

## 为什么必须单独放置

Code Fact 要回答代码事实；公司脚本决定工作区如何被取得、组装和提交。把两者混在一起会产生三个问题：

1. 通用能力被公司命令锁死，无法独立复用；
2. 第三方 Provider 的安装供应链与项目源码来源混为一谈；
3. AI 可能把“拉取成功”“索引成功”“提交成功”和“事实正确”误认为同一件事。

因此，Provider 只消费适配器输出的冻结快照，不直接理解公司命令。

## 两类身份必须分开

### Content ID

标识本次调查实际看到的内容，包括相关仓库文件、本地补丁、生成头/源、构建配置和必要外部输入的摘要。

### Provenance ID

标识这些内容从哪里来、如何组成，包括仓库与分支/修订、变更号、本地脏状态、submodule、LFS、稀疏检出、工作区脚本及其配置。

只记录 commit 不够：同一 commit 可能搭配不同生成物、本地补丁、submodule 或 LFS 内容；相同内容也可能来自不同交付路径。

## 推荐操作边界

| 动作 | 默认策略 | 原因 |
|---|---|---|
| 发现仓库、查看状态 | 允许只读 | 建立事实范围 |
| 生成修订冻结清单 | 允许写运行产物 | 不修改源码 |
| 创建任务工作区 | 需明确任务范围 | 会产生本地文件 |
| 拉取/同步 | 需明确策略或请求 | 可能改变用户当前工作区 |
| 提交/上传/合入 | 默认拒绝，必须有用户明确授权 | 外部高影响写操作 |

“无人值守运行”不等于“允许提交”。离开电脑期间可以继续做只读调查、生成运行产物和诊断；遇到提交权限或不可安全决定的工作区覆盖时，记录阻塞并继续其他独立工作。

## 多人协作与缺失仓库

工作区清单必须记录：

- 哪些仓库属于本次交付；
- 哪些仓库属于协作者且当前尚未交付；
- 是否存在接口/数据样本或权威设计；
- 缺失消费者对哪些结论形成证据上限；
- 用户提供的外部测试/构建输出对应哪个快照。

缺失协作者仓库不能被解释为“没有消费者”或“接口没被使用”。正确状态是外部依赖、覆盖不足或待对账。

## 实际接入前必须发现的事实

不得根据示例猜公司命令。接入时需从权威脚本文档和可执行工具中确认：

- 脚本路径、版本/摘要与责任人；
- 参数、配置和工作区布局；
- 失败时的退出码、标准输出/错误与部分成功语义；
- 认证方式和敏感字段；
- 拉取、清理、提交各自的副作用；
- 多仓修订如何冻结和重放；
- 本地修改如何保留或冲突；
- 提交动作如何获得用户显式授权。

这些事实确认并通过真实项目用例前，适配器保持 `DESIGNED / NOT_RUN`。
